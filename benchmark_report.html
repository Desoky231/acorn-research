Meeting Preparation & Baseline Analysis

Baseline Models & Architectural Limitations

Intuitive breakdowns of ACORN, SIEVE, and NaviX formatted according to research review standards.

ACORN: Predicate-Agnostic Search on Vector Graphs (SIGMOD '24) Single-Graph Baseline
💡 Main Idea

ACORN constructs a single unified graph index over the entire dataset and handles arbitrary predicates without building dedicated sub-indexes. To prevent graph traversal from getting trapped when encountering unmatching nodes, ACORN introduces gamma-expansion during construction. Instead of connecting each vector only to its immediate M nearest neighbors, it evaluates gamma × M candidates and selects edges spanning a diverse set of label attributes.

🧭 Traversal & Routing Mechanism

During search, ACORN traverses the graph guided by query distance. When it visits nodes that do not satisfy the query filter, it does not immediately discard them; instead, it uses them as bridge nodes to hop across unmatching regions of vector space and reach matching targets. Only nodes that satisfy the predicate enter the final top-k candidate heap.

⚠️ Limitations & Failure Modes

1. Low-Selectivity & Negative Correlation Collapse: When query filters are rare or negatively correlated (selectivity ≤ 0.2%), matching nodes become isolated islands. ACORN's fixed hop budget fails to cross long chains of consecutive unmatching nodes, causing Recall@10 to crash from 99% down to 0.00%.
2. Multi-Label Conjunction Degradation: On two-label conjunction queries with neutral correlation, recall plateaus at ~48% because the combined eligible subgraph becomes too sparse.
3. Index Build & Memory Overhead: Gamma expansion increases graph degree significantly during build, requiring more memory and longer indexing time (TTI).

SIEVE: Filtered Search with Collections of Indexes (PVLDB '25) Multi-Index Collection
💡 Main Idea

Instead of relying on a single graph and hopping over unmatching nodes, SIEVE organizes the dataset into a collection of specialized sub-indexes. For high-frequency predicates and popular filter combinations, SIEVE maintains dedicated pre-filtered sub-graphs. For unseen or arbitrary ad-hoc filters, it dynamically routes the query to the best-matching sub-index or falls back to an unconstrained graph with post-filtering.

🧭 Traversal & Routing Mechanism

When a filtered query arrives, SIEVE's query router evaluates the filter predicate against its index catalog. If a dedicated sub-graph exists for the filter, it executes a standard, uninterrupted HNSW search directly on that clean subgraph (achieving 100% recall with zero bridge hops). If no dedicated index matches, it uses selective routing to search a combination of overlapping sub-graphs and merges candidate lists.

⚠️ Limitations & Failure Modes

1. Severe Memory & Storage Bloat: Storing multiple overlapping sub-graphs across large label cardinalities consumes 2× to 5× more RAM and disk space than single-graph methods.
2. Cold/Ad-hoc Filter Degradation: If queries have rare, high-cardinality, or complex multi-attribute predicates not pre-indexed in the catalog, routing efficiency degrades and search falls back to slow scans.

NaviX: Native Vector Index for Graph DBMSs (PVLDB '25) Local Density Adaptive
💡 Main Idea

NaviX evaluates database predicates upfront and records eligible nodes in a bitmask. During search, it dynamically measures the local fraction of eligible neighbors around each candidate. If ≥ 40% of neighbors pass the filter, it performs standard 1-hop search. Otherwise, it adaptively chooses between directed 2-hop traversal and full 2-hop scanning based on a cost formula comparing edge evaluations.

🧭 Traversal & Routing Mechanism

The implementation compares fullCost = (degree × eligibleNeighbors + eligibleNeighbors) × 0.4 against directedCost = degree + (degree - eligibleNeighbors). It selects directed 2-hop when fullCost is larger, using query-relevant unmatching nodes as bridges toward eligible clusters.

⚠️ Limitations & Failure Modes

NaviX generally explores only up to two hops. If reaching an eligible cluster requires crossing a chain of 3 or more consecutive unmatching nodes, search gets permanently stranded, causing recall loss on sparse or negatively correlated predicates.

In-Depth C++ Source Audit

ACORN Codebase vs. Paper Findings

Architectural bottlenecks and discrepancies identified in ACORN.cpp and ACORN.h.

1. The "Predicate-Agnostic" Lie (Single Label vs. 32-Bit Limit) Data Structure Limit

The Code Reality: In ACORN.h, the index stores a flat array of single integers (const int* metadata;). Bitmasking overcomes this for SIFT1M, but is hard-capped at 32 total unique labels across the entire database. Real-world multi-attribute datasets (TripClick, LAION) fail completely.

const int* metadata; auto metadata = hnsw.metadata[nodeId]; // 1-to-1 array: strictly 1 integer per vector!
2. The "Filter Map" Memory Bomb (1 GB to 25 GB Overhead) Memory Bloat

The Code Reality: hybrid_search requires an uncompressed char* filter_map of size (nq × nb). For 1,000 queries on 1M vectors, that requires 1.0 GB of raw RAM. On LAION-25M, this requires 25 GB of RAM and immediately crashes.

3. Missing "Pre-Filtering Fallback" Implementation Missing Logic

The Code Reality: While the SIGMOD '24 paper claims ACORN automatically falls back to pre-filtering when the graph is disconnected, there is zero fallback logic in the official codebase. The search blindly traverses broken subgraphs.

4. M_beta Compression is ONLY Applied to Level 0 Edge Explosion

The Code Reality: In add_link, compression is guarded by if (level == 0). Upper graph layers are uncompressed and balloon to M × gamma edges, causing massive memory bloat.

5. Multi-Attribute & Inverse Correlation Breakdown Total Disconnection (0.00% Recall)

The Research Finding: While the SIGMOD '24 paper tests single keywords and claims ACORN solves correlation, our 3-dataset benchmark proves that under Negative Correlation (Lift = 0.05), ACORN achieves 0.00% Recall@10 across all efSearch settings. When tags avoid each other, matching vectors are isolated dots, causing multi-hop traversal to collapse completely.

💡 Significance: Empirically validates SIEVE's (PVLDB '25) core argument that collections of dedicated sub-graphs are necessary for complex multi-attribute queries.
